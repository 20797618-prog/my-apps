# 账号体系 · 可复用资料包

这是一套**可复制、可复用**的账号登录体系，供你以后开发的每一个程序共用同一套账号：
用户只要在任意一个程序里用邮箱登录过，之后打开你开发的**其他程序**，用同一个邮箱就能直接登录，**无需重复注册**。

支持两种登录方式（可自由切换）：
- **邮箱 + 验证码**登录（自动发邮件验证码，未注册自动建号）
- **邮箱 + 6 位数字密码**登录（用户登录后自行设置）

---

## 一、核心原理：为什么一套账号能「多应用复用」

关键在于：**账号数据并不是存在某个程序里，而是存在 Cloudflare 的一个独立 KV 里（`ACCOUNTS_KV`）。**

```
        ┌───────────────┐     ┌───────────────┐     ┌───────────────┐
        │   程序 A       │     │   程序 B       │     │   程序 C       │
        │  (网站导航)     │     │ (你以后写的)    │     │ (你以后写的)    │
        └──────┬────────┘     └──────┬────────┘     └──────┬────────┘
               │     都绑定同一个      │                     │
               └──────────►  ACCOUNTS_KV  ◄─────────────────┘
                          （中央账号库，账号数据唯一一份）
```

- 每个程序只需「绑定」同一个 `ACCOUNTS_KV` 命名空间（id 固定），
  用户在任何程序登录，读写的是**同一份账号数据**。
- 所以账号天然互通。**复制代码不会导致账号分裂**——复制几份代码都无所谓，
  只要绑的是同一个 `ACCOUNTS_KV`，账号就是通的。

> 结论：你之前担心的「复制文件夹会导致每个程序各自一套账号」不会发生。
> 因为数据只有一份（在云端 KV），代码只是「访问这份数据的工具」而已。

## 二、目录结构

```
account-system/
├── README.md                  ← 本文件（总览）
├── INTEGRATION.md             ← 新项目接入步骤（照做即可）

│   └── api/auth/
│       ├── request-code.js    发送验证码
│       ├── verify-code.js     校验验证码并登录
│       ├── login-password.js  密码登录
│       ├── set-password.js    设置/修改密码
│       └── me.js              校验当前会话
└── frontend/
    └── auth.js                ← 前端通用认证模块（浏览器直接引入）
```

## 三、接入方式对比（回答：是不是复制文件夹就行）

你有三种做法，按推荐度排序：

### 方式一：复制资料包到每个项目（★ 推荐，就是你设想的做法）

把 `backend/` 复制到每个新项目的 `functions/` 下，`wrangler` 绑定同一个 `ACCOUNTS_KV`，配置 secrets，完事。

- ✅ 优点：简单直观、每个项目自包含、可独立部署、离线也能看代码。
- ⚠️ 缺点：代码存在多份副本，将来若改认证逻辑，需要同步到每个项目。
- 👉 **适合你的场景**：账号逻辑已经很稳定，以后改动少，复制法最省心。

### 方式二：独立「账号中心」（进阶，一处维护）

把账号认证**单独部署成一个 Cloudflare 项目**（例如 `auth.xxx.pages.dev`），
所有新程序不再自带认证代码，而是直接调用这个中心的 `/api/auth/*` 接口。

- ✅ 优点：代码只有一份，改一处全生效，账号体系可独立升级。
- ⚠️ 缺点：需要多部署一个项目、多一次跨域调用（已支持 CORS）。
- 👉 适合：程序多到 5 个以上、且希望长期统一维护时再考虑。

### 方式三：Git 子模块（不推荐新手）

把 `account-system` 做成独立 git 仓库，各项目用 submodule 引用。

- ⚠️ 缺点：操作复杂、容易出「子模块版本不一致」问题，收益不明显。

> **给结论**：现阶段用**方式一（复制资料包）**即可，完全够用。
> 等以后程序多了、想统一维护，再平滑升级到方式二也不迟（接口完全一致，前端零改动）。

## 四、快速开始（三步）

1. **复制代码**：把 `backend/` 整个复制到新项目的 `functions/` 目录下。
2. **绑定 KV**：把 `wrangler.snippet.jsonc` 里的 `ACCOUNTS_KV` 绑定，合并进新项目的 `wrangler.jsonc`。
3. **配置 secrets**：按 `SECRETS.md` 配置 `MAIL_*` 环境变量。

前端在页面里 `<script src="auth.js"></script>`，然后调用 `AccountAuth` 即可。
完整步骤见 **[INTEGRATION.md](./INTEGRATION.md)**。

## 五、接口一览

| 方法 | 路径 | 说明 | 是否需登录 |
| --- | --- | --- | --- |
| POST | `/api/auth/request-code` | 发送登录验证码 | 否 |
| POST | `/api/auth/verify-code` | 校验验证码，签发会话 token | 否 |
| POST | `/api/auth/login-password` | 邮箱 + 6 位密码登录 | 否 |
| POST | `/api/auth/set-password` | 设置/修改密码 | 是（Bearer） |
| GET | `/api/auth/me` | 校验当前会话 | 是（Bearer） |

会话 token 通过请求头 `Authorization: Bearer <token>` 传递，有效期 30 天。

## 六、常见问题

**Q：新程序能拿到用户的所有数据吗？**
不能。账号库只存「账号本身」（邮箱、密码哈希、会话）。各程序自己的业务数据（如书签）
存在各自独立的 KV 里，互不可见。共享的只是「登录身份」。

**Q：密码安全吗？**
密码用 PBKDF2 加盐哈希存储（不存明文），且带防爆破锁定（连错 5 次锁 15 分钟）。

**Q：验证码发信会被限流吗？**
同一邮箱 60 秒内只能请求一次验证码；验证码 10 分钟有效。

**Q：以后想换邮箱服务商（不用 QQ 邮箱）？**
只需改 `MAIL_HOST` / `MAIL_PORT` 等环境变量即可，代码用标准 SMTP，通用。
